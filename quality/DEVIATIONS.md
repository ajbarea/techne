# Deviations from the pre-registration

Each entry is dated, gives its reason, and is named in the report. `PREREGISTRATION.md` itself does not change.

## 2026-10-29: task notes completed before the baseline restarts (#249)

**What changed.** `quality/tasks/tasks.toml`: the "Interface the tests use" note on eight of the ten tasks now states every name, message and rule the hidden tests check that the bug report did not give. sphragis-186 and sphragis-212 gained a note; techne-220, techne-162, techne-174, techne-166, techne-206 and sphragis-149 had theirs completed. The bug reports are unchanged. `quality/run.py --check-tasks` now also fails a task in three cases: a name or file that a hidden test's failure on the parent names and no code span in the report gives (a keyword argument, flag or subcommand the parent refused, which the fix added or stopped passing; a missing attribute, import or module the fix adds to its code; or a file the fix adds that a test loads or runs by path); new message wording a hidden test checks, shared with the strings the fix adds, that the report does not state; and a parent run that wrote no test results. It cannot see a rule stated only in prose, a new positional parameter, a name no failure names, a message under three words, or a non-Python file's unquoted text; a reading audit covers those, and found the completions on techne-220, -162, -174 and -166.

**Why.** The registration's task rule required these notes ("when a hidden test calls a name, checks a message, or asserts a rule from a removed Fix section that the parent tree lacks, the report ends with an "Interface the tests use" note that states it"), but the task set was committed with gaps no check caught. The completed notes go further: they also state rules the tests take from the fix PR itself, such as techne-206's nested-repository rule. The first four Opus baseline runs all failed their hidden tests. In three of them, nothing in the report could have told any model what the tests check: `artifacts()` (sphragis-186), `grants_file()` and the unreadable-file wording (sphragis-149), and the nested `CLAUDE.local.md` wording and nested-repo rule (techne-206). Every mode would fail such a task, so it would always score *d_t* = 0, which pulls a non-inferiority test toward "no difference" and hides a real loss ([ICH E10](https://gmp-compliance.org/guidelines/gmp-guideline/ich-e10-choice-of-control-group-and-related-issues-in-clinical-trials) calls this missing assay sensitivity). SWE-bench Verified removed tasks for the same two faults, an under-specified issue and tests that reject valid solutions ([OpenAI, 2024](https://openai.com/index/introducing-swe-bench-verified/)), and SWE-bench Pro adds interface notes like these ([Deng et al., 2025](https://arxiv.org/abs/2509.16941)).

**What it can bias.** It precedes any budget-mode run and applies to both modes, so it favours neither. The notes state what the tests check, not how to fix the bug. Task selection, risk classes, margin, metric and analysis are unchanged.

**The four void runs.** techne-206, techne-166, sphragis-149 and sphragis-186, repeat 3, normal mode, under the old task hash. They stay in `quality/results/2026-10-29-baseline-void/` and are reported, but they are not pooled: `analyze.py` already refuses a set whose input hashes differ. In techne-166, a quoted relative name with a backslash was accepted as a Chrome profile. The old note's "a Windows path" allowed that reading, so the note now says a drive-letter path. The run's reviewer flagged a different input in the same function (`lighthouse_profile`: a non-ASCII drive-letter path, whose octal escapes the unquote left in place). The folder also keeps `discards.jsonl`, whose one record is a techne-206 attempt that ended on an API error before the run that counted.

**Restart.** The baseline reruns from the start in `quality/results/2026-10-29-baseline-2/`, under the new task hash.

## 2026-10-31: leak flags labelled by a shell reader (#255)

**What changed.** The primary metric keeps the registered leak rule exactly; a test pins its three patterns to the registered text. `quality/run.py` also parses each Bash call with tree-sitter-bash, follows the shell's folder from call to call, and labels each flag: no label when a network program or registered folder is used, `text:` for a match it cannot show inert, and `cleared:` for one it shows inert. Only three shapes clear: a search's words, a local git command's words, and a pytest `-k`/`-m` expression, each only with a bare program name, nothing in the call that changes what a word runs, and output that reaches only the tool result. `extra:` marks a reach the rule misses. `run.py --reaudit` adds the labels to recorded runs.

**Why.** The registered rule matches text, so a grep pattern naming `curl` or a local `git stash push` fails a run. On the first 14 baseline runs it raised 50 flags on 12; the reader labels 20 cleared, 30 text, none as run. Six review rounds each found commands a clearing shape wrongly cleared, as expected, since a static reader of bash cannot be sound ([Mazurak and Zdancewic, 2007](https://repository.upenn.edu/cis_papers/590)). So the reader cannot move the registered outcome.

**What it can bias.** Nothing in the primary result. The report adds two sensitivity rows ([Thabane et al., 2013](https://pmc.ncbi.nlm.nih.gov/articles/PMC3720188/)): the reader's view, with cleared flags dropped and `extra:` flags counted (7 of the 14 runs flagged), and an upper bound on the relief that counts only flags it shows ran (none of the 14). A wrong clearing can only make the first row optimistic. Both modes get the same reader, fixed before any budget-mode run.
